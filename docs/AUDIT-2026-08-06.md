# Phase 1 — What exists today

## 1.1 Architecture

| Layer | Reality |
|---|---|
| Framework | Next.js 16 App Router, React 19.2, TypeScript strict, Tailwind v4 (CSS-first `@theme`) |
| Rendering | **Every one of the 28 routes is `ƒ` (dynamic)** — build output confirms zero static/ISR pages |
| Data | Prisma 6 → Postgres (Supabase Seoul). Singleton client in [db.ts](src/lib/db.ts) |
| Auth | Auth.js v5 beta, JWT strategy, edge/Node split ([auth.config.ts](src/auth.config.ts) / [auth.ts](src/auth.ts)) |
| Routing | Host-based two-domain split in [proxy.ts](src/proxy.ts) (apex = consumer, `studio.` = console) |
| i18n | next-intl, cookie-driven locale, no URL segment ([request.ts](src/i18n/request.ts)) |
| State | **No client state library.** `useState`/`useTransition` locally; server state via RSC + `router.refresh()`. `useSyncExternalStore` for rail collapse ([usePersistedCollapse.ts](src/lib/usePersistedCollapse.ts)) |
| Mutations | Server Actions only. No REST/tRPC. 5 route handlers exist purely for redirects + auth |
| Payments | `PaymentProvider` interface, **mock adapter only** ([payments/mock.ts](src/lib/payments/mock.ts)) |
| Identity | `VerificationProvider` interface, mock adapter only |

**Assessment:** the architecture is sound and unusually well-documented. The domain split, the
edge-safe auth config, the `tokenVersion` revocation gate, and the money-invariant isolation in
[mochi.ts](src/lib/mochi.ts) are all genuinely good decisions with recorded rationale. The problems
below are almost entirely *gaps*, not *mistakes*.

# Phase 2 — Gap analysis

Ordered by severity. Every item states **why it matters → user impact → complexity → priority**.

## 🔴 CRITICAL

### C1. Unbounded purchase quantity + always-succeeding mock PG = free mochi in production
`buySchema.quantity` is `z.number().int().positive()` with **no upper bound**
([marketplace-actions.ts:18](src/app/s/[handle]/marketplace-actions.ts#L18)). `buyMochi` then calls
the provider, which in production is still `mock` — and
[mock.ts:31-39](src/lib/payments/mock.ts#L31) **always returns `ok: true`** and grants
`req.quantity` mochi.

- **Why it matters:** any signed-in user can POST `quantity: 5_000_000` and receive 5M mochi without
  paying, then drain every creator's entire marketplace.
- **User impact:** creators owe real fulfillment against fabricated credit. Data corruption is
  permanent (`purchasedTotal`, `lifetimeSold`, leaderboards all poisoned).
- **Secondary:** `pricePerMochiKrw * quantity` and `soldQuantity` are Postgres `Int` (Int4). Above
  ~2.1B the transaction throws *after* the charge, hitting the compensation path.
- **Complexity:** Low (a `.max()` + a per-purchase KRW ceiling + a `MochiIssuance`-relative cap).
- **Priority:** **Critical — must be fixed before launch.** _(Re-scored 2026-08-06: pre-launch, so
  there is no live exploit. It stays first in the queue because it is ~1 line and gates the money
  model, not because it is currently being abused.)_

### C2. The live money path has no minor / age gate
`ageVerified` and `guardianConsent` are checked **only** in the dead
[`/s/[handle]/back` flow](src/app/s/[handle]/back/actions.ts#L30-L35). Neither `buyMochiAction` nor
`buyMochi` reads them. `/onboarding` records `ageVerified` and sets `guardianConsent: false` for
minors — and nothing ever consumes it.

- **Why it matters:** the 법령 carve-out in `/refund` explicitly promises a minor's payment is
  refundable. The product cannot honour a rule it never evaluates. 전자상거래법 exposure the moment
  `PAYMENT_PROVIDER` leaves `mock`.
- **User impact:** guardians have a statutory cancellation right the system can neither detect nor
  process.
- **Scope correction (2026-08-06):** narrower than first stated. `completeOnboarding` already
  hard-requires `verifiedAt` ([onboarding/actions.ts:92](src/app/onboarding/actions.ts#L92)) and the
  middleware forces onboarding, so every account reaching the buy *UI* is verified. The gap is
  reachable only by invoking the server action directly. Still worth closing — same one-line change.
- **Blocker on testing it:** [mock.ts:20](src/lib/verification/mock.ts#L20) hardcodes
  `isAdult: true`, so no account can currently be a minor and the gate cannot be exercised. Stage 0
  adds a minor-simulating mock mode.
- **Complexity:** Low to gate (Medium to build the guardian-consent flow, which is already
  out-of-scope-flagged in PROGRESS).
- **Priority:** **Critical — hard blocker on real PG.**

### C3. Zero error boundaries anywhere
`find src/app -name error.tsx -o -name global-error.tsx -o -name not-found.tsx` → **nothing**.

- **Why it matters:** a Prisma timeout, a Supabase blip, or any thrown error in a server component
  renders Next's default error screen — English, unstyled, no brand, no recovery path.
- **User impact:** a transient DB hiccup mid-purchase looks like a dead site. On a payments product
  that is a trust-destroying failure mode.
- **Complexity:** Low.
- **Priority:** **Critical.**

### C4. Metadata sells a retired product; no per-page metadata at all
[layout.tsx:16-20](src/app/layout.tsx#L16) is the **only** metadata in the app, and it still reads
_"팬의 응원을 매달 한 장의 **트러스트 리포트**로"_ — the thesis removed in DECISIONS 2026-08-01.

- **Why it matters:** every page — landing, every creator profile, every marketplace — shares one
  title/description describing a product that no longer exists. No `openGraph`, no `twitter`, no
  `metadataBase`, no `sitemap.ts`, no `robots.ts`, no OG image.
- **User impact:** a creator sharing `/s/handle` to KakaoTalk/X/Discord gets a card with the wrong
  pitch, the wrong name, and no image. **Sharing a creator page is the product's primary organic
  growth loop, and it is currently broken.** Search results are equally wrong.
- **Complexity:** Low–Medium (`generateMetadata` per route; OG images are Medium).
- **Priority:** **Critical — highest ROI item in the entire audit.**

### C5. Unknown creator handles return HTTP 200
[s/[handle]/page.tsx:37-56](src/app/s/[handle]/page.tsx#L37) renders a styled "not found" body but
never calls `notFound()`.

- **Why it matters:** search engines index every typo'd/deleted handle as a real page. Monitoring
  can't distinguish a 404 from a success.
- **Complexity:** Trivial (`notFound()` + `not-found.tsx`).
- **Priority:** **Critical** (bundled with C4, same work session).

## 🟠 HIGH

### H1. Mobile navigation does not exist
The Sidebar is `hidden lg:block` ([SidebarPanel.tsx:49,63](src/components/SidebarPanel.tsx#L49)); the
RightRail is `hidden xl:block` ([RightRailPanel.tsx:35,49](src/components/RightRailPanel.tsx#L35)).
The header ([Nav.tsx](src/components/Nav.tsx)) has no hamburger, no drawer, no bottom bar — signed
in, it is brand · ranking icon · bell · Studio pill · avatar.

- **Why it matters:** below 1024px, **홈 and 둘러보기 links vanish entirely**, along with the whole
  following list. The only route to `/explore` is a footer link at the bottom of the page.
- **User impact:** Korean creator-economy traffic is overwhelmingly mobile. The primary discovery
  surface is effectively unreachable for the majority of users.
- **Evidence of scale:** only 17 `lg:` and 8 `md:` utilities exist across the entire codebase vs 114
  `sm:` — the app was designed at desktop width and narrowed, not built mobile-first.
- **Complexity:** Medium (bottom tab bar + drawer for the following list).
- **Priority:** **High — arguably the largest addressable-audience gap.**

### H2. No loading states, no Suspense, no skeletons
Zero `loading.tsx`, zero `<Suspense>` in the codebase.

- **Why it matters:** every navigation blocks on the full server render. `/s/[handle]` issues ~9
  queries plus the rails' ~5 before a single byte ships. Cross-Pacific latency (see H5) multiplies
  this.
- **User impact:** clicking a creator feels like nothing happened for 400–1200ms. Filter changes on
  `/explore` (`router.push` with no `useTransition`) freeze the current view with zero feedback.
- **Complexity:** Medium.
- **Priority:** **High.**

### H3. No security headers; open image proxy
[next.config.ts](next.config.ts) sets no `headers()`. Missing: CSP, HSTS, `X-Frame-Options`/
`frame-ancestors`, `Referrer-Policy`, `X-Content-Type-Options`, `Permissions-Policy`.
`images.remotePatterns` is `{ protocol: "https", hostname: "**" }` — **any host on the internet**.

- **Why it matters:** no clickjacking defence on a payment flow. The wildcard image pattern is a
  standard Next.js SSRF/bandwidth-abuse vector (`/_next/image?url=...`) — and it is pure risk with
  zero benefit here, because **`next/image` is used exactly 0 times** (5 raw `<img>` instead).
- **Complexity:** Low.
- **Priority:** **High.**

### H4. No rate limiting on any server action
`buyMochiAction`, `redeemItemAction`, `toggleFollow`, `markAllRead`, the handle-availability check,
and every auth action are unthrottled.

- **Why it matters:** compounds C1. Also enables credential stuffing on the credentials provider,
  notification-table flooding via `upsertItem`, and follow-spam.
- **Complexity:** Low–Medium (no dependency needed if a `Postgres` counter table is acceptable;
  Upstash is the conventional choice but adds a dependency).
- **Priority:** **High.**

### H5. Query and caching profile is unsustainable
- **Every signed-in page render** invokes `RightRail`, which calls
  [`getExploreStreamers`](src/lib/streamers.ts#L55) — a **full unpaginated table scan** of all
  approved creators, each with a `_count` subquery, then filters and sorts **in JavaScript**. There
  is no `take`, no `skip`, no DB-level `ORDER BY`.
- `getFollowList` runs **twice per page** — once in `Sidebar`, once in `RightRail`
  ([Sidebar.tsx:19](src/components/Sidebar.tsx#L19),
  [RightRail.tsx:26](src/components/RightRail.tsx#L26)) — identical query, no dedupe (React `cache()`
  is not used anywhere).
- `getMyRankings` is **N+1**: one `getSupporterRank` per holding, each 3 queries → 13 queries for a
  user holding 4 creators ([ranking.ts:40](src/lib/ranking.ts#L40)).
- `getAffordableItems` is N+1 per held creator ([home.ts:84](src/lib/home.ts#L84)).
- `getOrdersForBacker` fetches **all orders ever** then filters `pending` in JS
  ([HomeSignedIn.tsx:63](src/components/HomeSignedIn.tsx#L63)).
- **Zero caching primitives** anywhere: no `unstable_cache`, no `revalidate`, no `cache()`, no tags.
- ~~`vercel.json` requests `icn1`, but Hobby ignores region pinning~~ — **resolved 2026-08-06: the
  account is Vercel Pro, where single-region pinning is honoured.** Functions run in `icn1` beside
  the Seoul database. This removes the suspected cross-Pacific multiplier and **downgrades H5 from
  a latency problem to a scaling problem** — the queries are still wrong, but each round trip is
  ~1ms rather than ~150ms. `PROGRESS.md` and `DEPLOYMENT.md` both still assert the Hobby caveat and
  must be corrected.
- **Complexity:** Medium.
- **Priority:** **High** — unchanged. A full table scan per page render still fails at ~1k creators;
  it just fails later than feared.

### H6. `/refund` promises a support channel that does not exist
[Footer.tsx:83-92](src/components/Footer.tsx#L83) — all six support/company links are `href="#"`.
Additionally `/dashboard` ([Footer.tsx:61](src/components/Footer.tsx#L61)) **does not exist** and
404s; the route is `/studio`.

- **Why it matters:** the refund policy instructs users to contact 고객센터. A policy that names an
  unreachable channel is worse than no policy — it is a documented, self-inflicted compliance gap.
- **Complexity:** Low (an email address closes it; a real 고객센터 page is Medium).
- **Priority:** **High.**

### H7. Modal has no focus trap and no focus restore
[Modal.tsx](src/components/ui/Modal.tsx) focuses the card on open but never constrains Tab, and never
returns focus to the trigger on close.

- **Why it matters:** WCAG 2.2 **2.1.2 (No Keyboard Trap)** and **2.4.3 (Focus Order)**. Keyboard
  users tab straight out of the dialog into the page behind it.
- Also: `MarketplaceSection`'s cancel button is a bare `✕` glyph with **no accessible name**
  ([MarketplaceSection.tsx:219](src/components/MarketplaceSection.tsx#L219)) — announced as
  "✕, button".
- **Complexity:** Low.
- **Priority:** **High** (accessibility is a stated project value — `:focus-visible` and
  `prefers-reduced-motion` are already handled at the root, so this is an inconsistency, not a
  philosophy gap).

### H8. Explore search discards the user's other filters
The search field is a native `<form action="/explore">` containing only `name="q"`
([ExploreFilters.tsx:55-67](src/components/ExploreFilters.tsx#L55)). Submitting it produces
`/explore?q=…` — **silently dropping** any active `type`, `category`, `backerRange`, and `sort`.

- **User impact:** filter, then search, and your filters vanish with no explanation.
- **Complexity:** Trivial (hidden inputs, or lift search into the same `setParam` mechanism).
- **Priority:** **High** (it is a plain bug, cheap to fix).

### H9. Spending mochi is irreversible behind one unconfirmed click
`ItemCard` opens a note textarea, then 구매 debits immediately. No summary of "you will spend N
mochi, leaving M", no confirmation step, no undo. Compare: cancelling is a *creator-only* capability
([mochi.ts:268](src/lib/mochi.ts#L268)) — **the buyer cannot cancel their own order at all**.

- **Why it matters:** irreversible value transfer with a single click and no confirmation is below
  the floor for any commerce product.
- **Complexity:** Low (confirm step) / Medium (buyer-initiated cancellation window).
- **Priority:** **High.**

### H10. User-facing copy hardcoded in source
- All five notification titles/bodies are Korean template literals in
  [studio/actions.ts](src/app/studio/actions.ts#L102-L103,L298,L364,L391).
- [creators/page.tsx](src/app/creators/page.tsx#L70-L118) has ~10 hardcoded Korean strings
  (크리에이터A, 나의 마켓, 실시간 샤라웃, 멤버 전용 포스트, 노래 신청, +312 응원, 직접 정산, …).
- `ComingSoon` hardcodes `"motoo for creators"` ([ComingSoon.tsx:31](src/components/ComingSoon.tsx#L31)).
- `StreamerCard` hardcodes `명` ([StreamerCard.tsx:41](src/components/StreamerCard.tsx#L41)).
- **Why it matters:** violates a stated hard constraint in CLAUDE.md, and these strings are invisible
  to `check:vocab`'s copy review.
- **Complexity:** Low.
- **Priority:** **High** (it is an explicit project invariant currently being violated).

## 🟡 MEDIUM

### M1. `en.json` is 745 keys of unreachable dead weight — ✅ DECIDED: delete
`LOCALE_COOKIE` is documented as "set by the language switcher" — **no language switcher exists**
anywhere in `src/`. Every user gets `ko`. 41KB of English translation is maintained and shipped for
nobody.

**Decision (2026-08-06): delete `en.json`. Korean-only at launch.** Moves to **Stage 8**, and
collapses the locale plumbing: `locales` becomes `["ko"]`, `LOCALE_COOKIE` and the cookie read in
[request.ts](src/i18n/request.ts) can go, and `hasLocale` in [layout.tsx](src/app/layout.tsx#L26)
simplifies to a constant. Keep next-intl itself — it is what keeps copy out of components, which is
a stated project invariant independent of how many languages ship.

### M2. Pretendard loads via CDN `@import`
[globals.css:2](src/app/globals.css#L2) — a render-blocking `@import` to jsdelivr inside the critical
CSS, on a Korean-market product where jsdelivr is not consistently fast. Blocks first paint, adds a
third-party single point of failure, and forecloses CSP `style-src 'self'`. Self-host via
`next/font/local` (subset to the Korean range) or `next/font` with `display: swap`.

### M3. No pagination anywhere
Explore (all creators), profile order history (all orders), notifications (fixed 30, no "load more"),
supporter leaderboard (fixed 60), studio orders (all). Each is fine at seed scale and breaks
silently at real scale.

### M4. Dead code — ~700 LOC
`/s/[handle]/back` + [BackingFlow.tsx](src/components/BackingFlow.tsx) (505 LOC, retired vocabulary,
routable), [grades.ts](src/lib/grades.ts) (100 LOC, **zero importers**), `/apply` (stub linked from
nowhere), 8 dormant Prisma models, `Backer.currencyBalance`, `Streamer.followerCount`.
Note the irony: the dead flow is the **only** place the age gate is implemented (C2).

### M5. Missing layout abstraction — `<Nav/>` + `<Footer/>` repeated across 22 pages
No route groups. Every page manually composes `<Nav/>`, its body, and `<Footer variant="fan"/>`.
`(marketing)`, `(app)`, and `(auth)` route groups with their own `layout.tsx` would delete the
repetition and make the `ConsumerShell` boundary structural rather than conventional.

### M6. Duplicated abstractions
- [SignupModal.tsx](src/components/SignupModal.tsx) predates `ui/Modal` and carries its own portal /
  Escape / scroll-lock copy (already logged in PROGRESS).
- [studio/page.tsx:34](src/app/studio/page.tsx#L34) defines a **local `Section`** shadowing
  `ui/Section` — two components, same name, different contracts.
- Form inputs, selects, textareas, chips, and stat tiles are re-styled inline in 3–8 places each with
  drifting values.

### M7. Fabricated metric on the marketing landing
[page.tsx:221](src/app/page.tsx#L221) renders `formatCount(spotlight.backerCount * 10)` labelled as
the creator's mochi total. It is invented. On a product whose entire premise is *trustworthy* support
data, a made-up number on the homepage is a real (if small) integrity problem — and the true value is
one `getSupporterLeaderboard` call away.

### M8. `revalidatePath` fan-out is brittle
[toggleFollow](src/lib/follows.ts#L68-L74) hardcodes 7 paths. Every new ConsumerShell page must
remember to add itself. Tag-based revalidation, or simply relying on these routes already being
dynamic, is correct.

### M9. All errors are swallowed
15 bare `catch {}` blocks. Server actions uniformly return `{ ok: false, error: "generic" }` with no
logging. The only `console.error` in the codebase is in `notify.ts`. **There is no error tracking,
no structured logging, and no analytics.** In production, a failing purchase is invisible to you.

### M10. Edge middleware doesn't check `tokenVersion`
Already documented in PROGRESS as deliberate (Prisma-free by design). Correctly scoped as *routing,
not authorization* — every page-level `auth()` does the real check. Listed here only for
completeness; **no action recommended.**

### M11. `parseImageDataUrl` regex-tests before length-checking
[imageUpload.ts:78-79](src/lib/imageUpload.ts#L78) runs `DATA_URL_RE.test(value)` on an
attacker-controlled string of arbitrary length, *then* checks `maxBytes`. The pattern is
low-backtracking so this isn't a live ReDoS, but the checks are in the wrong order for free.

### M12. Onboarding is a form, not an onboarding
Nickname + handle + 본인인증 + terms, then the user is dropped on `/home`. No welcome, no product
tour, no first-follow prompt, no empty-state guidance beyond the three-step primer. Industry standard
is a guided first-action ("follow 3 creators to fill your feed").

## 3.1 Industry-standard — expected, currently missing

| Convention | motoo today | Gap |
|---|---|---|
| Mobile-first navigation (bottom tab bar) | Desktop rails only, `lg:`+ | **H1** |
| Rich share cards per creator page | One global, wrong, retired title | **C4** |

> **PIPA note (개인정보 보호법):** Korean law grants users a right to deletion and to access their
> personal data. `/settings` offers profile picture, nickname, handle, and password — **there is no
> way to delete an account or export data.** This belongs with the counsel review, not as a
> nice-to-have.

## 3.2 The underlying principles worth adopting (not the designs)

1. **The creator page is the product's front door, not its detail view.** Patreon, Ko-fi and Toonation
   all treat the creator URL as the canonical shareable object — optimized metadata, fast first
   paint, works logged-out. motoo's `/s/[handle]` is currently its *least* optimized page: fully
   dynamic, ~14 queries, no metadata, soft-404. Inverting this is the single highest-leverage change
   available.
2. **Money surfaces earn their friction.** Every mature product makes spending *slower* than
   browsing — a summary, a confirmation, a receipt. motoo currently makes spending the fastest
   interaction in the app.
3. **The empty state is the onboarding.** Ko-fi and Patreon use the zero-state as a guided first
   action. `HomeSignedIn`'s three-step primer is a genuinely good instinct — but all three steps link
   to the same `/explore`, so it teaches without actually branching.
4. **Progressive disclosure in creator consoles.** `ItemsManager` at 657 LOC is a single monolithic
   surface; Gumroad/Patreon split item CRUD, orders, and settings into distinct views with their own
   URLs.
5. **Korean products lean harder on trust chrome than Western ones** — 사업자등록번호, 통신판매업신고,
   대표자명, 고객센터 in the footer are near-universal and read as legitimacy signals. `t("businessInfo")`
   exists; the surrounding support links do not.

## 3.3 Nice-to-have

Creator analytics dashboard · saved/wishlist items · gift-mochi-to-another-fan (⚠️ conflicts with
non-transferability — likely must be declined) · supporter badges/tiers by lifetime purchase ·
scheduled item drops · creator-to-supporter broadcast (the `Update` model already exists and is
unwritable from any UI).

## 3.4 Innovative — differentiators worth considering

- **The `Update` model is already there and has no authoring UI.** A creator posting to their
  supporters is the retention loop the product currently lacks entirely. Lowest-cost genuine
  differentiator available — the schema, the read queries, and the profile rendering all exist.
- **Rank-as-narrative.** `getSupporterRank` is computed and shown but never *changes* anything.
  "You're #4 — 20 mochi from #3" converts a static number into a loop.
- **Fulfillment SLA transparency.** Orders sit `pending` with no promised-by date. A creator-set
  fulfillment window, publicly displayed, is exactly the trust primitive the retired Trust Report
  was reaching for — at a fraction of the complexity.

## Stage 7 · Account, Settings & Compliance
**Effort:** 3–4 days · **Risk:** 🟡 Medium (legal surface) · **Depends on:** Stage 2

### Still needing an answer before their stage

- ~~**Stage 7:** grace-period length~~ ✅ **30 days**, confirmed 2026-08-06.
- **Stage 7: does the deleted user get their money back?** ⚠️ **Open, and it is a money invariant,
  not a detail.**

  Returning unspent units to the creator's supply is settled. But payment goes **directly to the
  creator's sub-merchant** at purchase time (`settleToStreamer`, spec §8) — motoo never holds the
  funds. So if a fan pays ₩10,000 for 50 mochi, never spends it, and their account is purged:

  | | today's rule | consequence |
  |---|---|---|
  | Creator | already received ₩10,000 | can now **sell the same 50 units again** → paid twice for one fulfillment obligation |
  | Deleted user | balance returns to supply | receives **nothing** |

  That is double-payment by construction, and forfeiting prepaid credit (선불전자지급수단) is
  precisely what Korean law is least likely to permit. Two readings, and they need different code:

  1. **Refund then return** — void/refund the unspent portion to the user's original payment method,
     *then* return the units to supply. Coherent, no double-payment, but needs a working refund path
     through the PG (which the mock's `voidCharge` only stubs).
  2. **Return only** — units go back, money stays with the creator. Simpler, and what the literal
     answer describes, but the user is out of pocket with nothing to show, which reads as
     forfeiture.

  Note this also has to agree with `/refund`'s existing **60% rule** (잔액 환불 once 60% is spent) —
  a user below that threshold who deletes their account would otherwise get a *better* outcome by
  deleting than by asking for a refund, which is an incoherent policy.

  **Take reading 1 vs 2 to counsel with the termination clause.** Stage 7 builds this as one
  swappable policy function either way, so it does not block the deletion flow.
